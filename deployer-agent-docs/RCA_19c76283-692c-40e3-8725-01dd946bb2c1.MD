# RCA — crypto-conex redeploy blocked (deployment_blocked / phishing gate)

## Summary
The redeploy could not go live because the deployment is under a **platform trust-and-safety (phishing-classification) block**. This is not a source, manifest, secret, tier, or infra-provisioning fault — the build itself succeeded.

## Evidence
- `trigger_indie` returned HTTP **409** `{"code":"deployment_blocked","error":"This deployment was blocked. If you believe this is a mistake, please contact support."}` (non-retryable).
- Most recent failed run `19c76283-692c-40e3-8725-01dd946bb2c1` terminated at the **`await_phishing`** phase:
  `"deployment blocked: there has been an error with this deployment. Please fork the session and start a new deployment"`.
- `get_step_status` for that run: `build` = **success**; `mongodb_migrate`, `manage_secrets`, `deploy`, `health_check` all = `"not run: an earlier deploy step failed"`. So the pipeline never reached any app-level step — it was gated before deploy.
- Deployment is otherwise healthy: active run `e32451f9-37e1-4de9-bb5a-47d7813ff9e0` is `success` and serving at https://crypto-conex.emergent.host.

## Root cause
A trust-and-safety / phishing classifier flagged this deployment and set a hard block. The block is enforced at the platform layer above the deploy pipeline and returns a non-retryable 409 on every trigger.

## Why no fix was applied
There is no manifest, code, secret, or tier change that clears a trust-and-safety block. Re-firing the pipeline would deterministically return the same 409. No `resume_pipeline` was attempted for this reason.

## Required action
- The user must **contact Emergent support** to review/lift the block (quote deployment_id `c00f34e1-af72-4be6-bb64-43844dd82c8f` and job_id `125c9cf8-92bc-4c4d-b9e2-574f7976e7ab`). The platform message also suggests forking the session to start a fresh deployment.
- The currently live version (active run `e32451f9`) remains up and serving in the meantime.
